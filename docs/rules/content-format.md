# Content Format

## 目标

本文件定义 Feeds Hub 每条 Markdown 内容的标题、摘要和正文格式。

核心目标：

- 直接写事实。
- 减少解释性判断。
- 避免观点化、预测化和标题党。
- 保持每条 feed 只对应一个事件。

## 全局写作原则

### 必须

- 使用已核验来源中的事实。
- 明确主体、动作、时间、状态和来源。
- 一条内容只写一个事件。
- 事实不完整时，用低确定性表达。
- 正文保持短段落，优先 2 段，最多 3 段。

### 禁止

- 不写“为什么重要”。
- 不写“这意味着”“影响深远”“重磅”“史诗级”等判断。
- 不写未经来源支持的预测。
- 不写投资建议、赛事预测或产品成功判断。
- 不把社交热度当作事实。
- 不把多个事件拼成一条。

## Title

标题只写核心事实。

格式建议：

```text
主体 + 动作 / 状态 / 结果
```

示例：

```text
OpenAI 发布新模型接口更新
Rust 项目发布 1.x 版本
某指数收盘上涨，芯片板块走强
某队晋级下一轮
```

避免：

```text
重磅！某公司震撼发布
这件事可能改变行业
某队迎来命运之战
```

## Subtitle

副标题补充来源、范围或状态，不写判断。

格式建议：

```text
来源 + 已确认事实 / 时间 / 范围
```

示例：

```text
官方公告显示，该更新已面向开发者开放
Reuters 报道称，相关决定仍待正式文件确认
比赛结束后，官方赛程显示下一轮对阵已确定
```

## Summary

摘要只写 1 句话，说明事实和当前状态。

要求：

- 不超过 80 个中文字符优先。
- 不写结论性判断。
- 不写未证实推测。
- 股市内容可以加入市场情绪。

示例：

```text
官方公告显示，该项目发布新版本，更新范围包括 CLI、配置和文档。
Reuters 报道称，相关政策仍在讨论阶段，正式文件尚未公布。
A 股收盘分化，芯片板块偏热，地产和消费板块偏冷。
```

## 正文通用结构

默认使用 2 段：

```text
第一段：事实。
第二段：当前状态、市场情绪、赛程节点、可确认范围或待确认信息。
```

需要补充来源差异时可以使用第 3 段：

```text
第三段：不同来源之间的差异、尚未确认的信息或后续已排期节点。
```

## 主题格式

### `worldcup`

正文只写赛事事实。

结构：

```text
第一段：比赛、赛程、赛果、晋级或官方节点。
第二段：当前阶段、下一场、下一轮、分组状态或待确认赛程。
```

可写：

- 比赛时间
- 比分
- 晋级和淘汰状态
- 下一轮或下一场节点
- 官方确认的伤停或阵容事实

禁止：

- 赛事预测
- 情绪化胜负判断
- “关键意义”“历史性影响”等判断

### `lol`

正文只写赛事和官方竞技事实。

结构：

```text
第一段：赛事、赛程、赛果、阵容、规则或官方公告。
第二段：分组、晋级、下一场、版本状态或待确认信息。
```

可写：

- 赛程和赛果
- 晋级和淘汰
- 官方赛制
- 战队公告
- 版本或规则变化

禁止：

- 训练赛传闻
- 胜负预测
- 没有来源的选手状态判断

### `stock`

正文只写市场事实，可以加入市场情绪。

结构：

```text
第一段：市场、指数、公司、政策、财报或宏观数据事实。
第二段：市场情绪：上涨 / 下跌 / 分化 / 震荡 / 偏热 / 偏冷。说明对应板块或资产。
第三段可选：风险提示或尚未确认的数据口径。
```

市场情绪写法：

```text
市场情绪：偏热，主要集中在芯片、AI 基础设施和电力设备方向。
市场情绪：分化，成长板块走强，消费和地产偏弱。
市场情绪：偏冷，主要指数回落，避险资产走强。
```

禁止：

- 买入、卖出、持有建议
- 收益判断
- 目标价
- 个性化投资建议
- 没有时间戳的价格描述

### `ai`

正文只写发布、研究、产品、工具或政策事实。

结构：

```text
第一段：主体发布、更新、论文、政策或工具变化。
第二段：当前开放范围、版本状态、适用对象、来源状态或待确认信息。
```

可写：

- 官方发布内容
- 模型、API、工具或论文状态
- 开源仓库变化
- 文档和模型卡中的范围说明
- 报道与官方信息的差异

禁止：

- 能力夸大
- AGI 判断
- 没有 benchmark 上下文的性能结论
- 未核验路线图

### `global`

正文只写综合新闻事实。

结构：

```text
第一段：地点、机构、主体、动作和时间。
第二段：已确认措施、影响范围、公开文件或仍未确认的信息。
```

可写：

- 官方决定
- 政策文件
- 法院裁决
- 国际组织报告
- 已确认公共事件信息

禁止：

- 阴谋化解释
- 情绪化描述
- 无来源伤亡或损失数据
- 未确认突发消息

### `rust`

正文只写工程事实。

结构：

```text
第一段：项目、版本、RFC、crate、工具链或安全公告事实。
第二段：变更范围、受影响组件、迁移要求、修复状态或文档位置。
```

可写：

- release note
- crate 版本
- RFC 状态
- GitHub PR / issue / advisory
- 迁移步骤，只限来源明确时

禁止：

- 没有证据的性能判断
- 泛泛称“更安全”“更快”
- 无来源的采用规模

### `product`

正文只写产品事实。

结构：

```text
第一段：产品、公司、功能、定价、平台规则或页面变化。
第二段：上线范围、用户可见变化、适用对象、公开页面或待确认信息。
```

可写：

- 产品发布
- 功能更新
- 定价页变化
- changelog
- App Store 更新说明
- 官方公告

禁止：

- 脱离事件的产品建议
- 成功学判断
- 增长确定性判断
- 无法核验的收入或用户数截图

## 不确定信息写法

可以写：

```text
目前官方文件尚未公布。
该信息来自媒体报道，仍需等待官方确认。
公开页面尚未显示完整范围。
不同来源对时间表表述不一致。
```

不要写：

```text
基本可以确定。
大概率会发生。
很可能带来巨大变化。
```

## Markdown 正文长度

建议：

- 2 段优先。
- 每段 1 到 2 句。
- 单条正文控制在 120 到 260 个中文字符。
- 长背景、深度分析和观点内容应放到 blog，不放到 Feeds Hub。

## Frontmatter 衔接

- `title` 写核心事实。
- `subtitle` 写来源、状态或范围。
- `summary` 写一句事实摘要。
- `priority` 只用于排序，不在正文里解释。
- `tags` 只保留实体、主题和类型，不写情绪标签。
